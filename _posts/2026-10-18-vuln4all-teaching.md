vuln4all 是我自己写的一个模块化 Web 漏洞靶场：在 `modules/<分类>/<名字>/` 放一个 `module.py`，重启，首页就多一道题。目前 22 个类别、46 道题。

这篇不是"摸到一个陌生站"的记录：每道题的洞埋在哪、为什么这么埋，我从第一秒就知道。知道答案的测试会失真，所以打的时候尽量假装第一次见 —— 判定统一用靶场自己的 `objective`，不看页面文案。`python3 main.py check --json` 里每道题有布尔值，两个都为 true 才算通关。只看一个，很容易把"满足了一半"当成打穿了。

## 一、题面本身就是索引

首页把所有模块按分类列出来，还带搜索和难度筛选；`/__vuln4all/status` 是体检页；`main.py list --json` 能拿到每道题的分类、CWE 编号和难度。

对做题的人来说这是方便，对真实目标来说这就是**信息泄露**。所以第一件事永远是看部署残留：

```
.env(200)  .git/HEAD(200)  .git/config(200)  deploy.sh.bak(200)
app.py.bak(200)  index.html.swp(200)  robots.txt(200)
```

而 `app.py`、`backup.zip`、`www.zip`、`.env.bak` 是 404。这个对照挺说明问题：**能不能拿到源码，往往取决于运维当时顺手删了什么**，跟站做得好不好关系不大。

## 二、同一个注入点，三种说话方式

`sqli` 那十一题里，最有意思的不是 payload，是**信道**。

- 结果会回显 ⇒ 走 UNION。先试列数：三列能对齐（`id`、`name`、`price` 三个渲染位）。
- 只告诉你"对不对" ⇒ 走布尔。这题的页面会回 `class="notice notice-ok"` 或 `notice notice-bad`，这两串就是现成的布尔信道。
- 什么都不说 ⇒ 走时间。`SLEEP` 在 SQLite 里按行求值：表里 3 行、睡 1 秒，实测回包 2.02 秒；基线 0.01–0.03 秒。阈值取 1.2 秒，远高于基线、远低于命中，稳定。

同一个注入，三种信道选哪个，取决于**对方愿意告诉我什么**。这是我觉得 injection 里最该练的一件事 —— 而不是背 payload。

还有一道值得单说：**二次注入**。注册时用户名带 payload，注册本身没问题（库里存的就是那个字符串）；等到"改密码"的时候，语句变成 `UPDATE users SET password = ? WHERE username = 'admin'--'`，劫持就发生在这一步。

> 净化发生在入口，不等于存储是安全的。真正的危险点是每一次**拼接**。

## 三、`os.path.join` 会把你给的绝对路径当老大

路径穿越那题的核心只有一行：

```python
os.path.join("/srv/data", "/etc/passwd")   # == "/etc/passwd"
```

不是"读了 `../`"，而是**第二个参数以 `/` 开头时，第一个参数直接被丢掉**。修法也不难，三道一起上：

```python
p = os.path.realpath(os.path.join(BASE, name))   # 归一化 .. 和符号链接
assert p.startswith(BASE + os.sep)                # 末尾的 os.sep 是必须的，防 /srv/data-evil
assert not os.path.isabs(name)                    # 或者干脆只允许 basename
```

第二行那个 `os.sep` 是很多人漏掉的：只比较 `startswith(BASE)`，`/srv/data-evil` 也能过。

## 四、编码是两层的，所以要编两次

有一题的过滤器会拦明文里的 `../` 和 `token`。绕过是这么过的：

```
%252e%252e%252f              → 第一次解码得 %2e%2e%2f，第二次得 ../
ops-%2574oken.txt            → 第一次解码得 ops-%74oken.txt（不含 "token" 字面量），第二次得 ops-token.txt
```

关键不是"双写编码"这个技巧，而是理解：**过滤器解码一次，运行时又解码一次**。所以只要第一层解出来的东西仍然"看起来干净"，就能过。

## 五、JWT 的三个老毛病

`jwt` 那几题把最常见的三种都放了一遍：

- **`alg: none`**，服务端照签照收 —— 声明部分是我写的，没人验。
- **`kid` 当路径用**：`"kid":"rotate-2026.key"` 被拿去拼文件名，补上 `../` 就能指向自己控制的密钥文件。
- **空密钥**：密钥为空时，用空串签出来的 token 居然验得过。

三个都是同一类：**把 token 里的元数据当可信输入**。修法也一致 —— `kid` 只允许白名单里的值、`alg` 只允许服务端配置的那一种、密钥长度不足直接拒绝启动。

## 六、钱退了，状态没变

业务逻辑那题我印象最深。正常流程是：付款 → 发货 → 退款。打法是：

1. 退款 ⇒ 响应说"退款已处理。**注意：订单状态没有变化。**"，`refunded=1`，状态还是"已发货"；
2. 确认收货 ⇒ 状态变成"已完成"；
3. 于是同一笔订单**既是已退款、又是已完成**。

问题不在退款逻辑，而在**"退款"被实现成了一个布尔标记，而不是状态迁移**。正确做法是把订单状态写成状态机：

```
待付款 → 已付款 → 已发货 → 已完成
                     ↘ 已退款（终态，不可再迁移）
```

每一次迁移校验"当前状态是否允许"，用事务加行锁保证原子性，退款还要幂等（带 `request_id` 去重）。同一类的还有竞态那题：并发领券领到 24 张，余额 2400 —— 单张 100 的券，余额却是 2400，这就是没有行锁的直接后果。

## 七、靶场本身的设计取向

写这 46 道题，反过来也把"怎么把东西讲清楚"练了一遍：

- **模块化**：加一道题就是加一个目录，不碰核心。这让我可以按"一个知识点一道题"来铺，而不是凑数量。
- **每题自带重置 / 提示 / 答案**：提示和答案是折叠的，做题的人可以卡住先看提示；重置是原子的，不会把别的题搞坏。
- **判定用 objective**：页面文案可以随便写，`check --json` 里的布尔才是权威。这条对真实项目也成立 —— 别拿"页面说成功了"当证据。
- **`doctor` 会返回非 0 退出码**：能直接挂 CI，新增模块的契约（挂载点冲突、硬编码路径）在合并前就被拦下。

最后说句实话：写完一遍再从头打一遍，最有价值的不是那 46 个 flag，而是**七个我到现在还记得的点**。其余的过了就忘了 —— 这也正常，payload 会忘，成因不会。
